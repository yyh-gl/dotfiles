## 目的

git diffの実装内容を、**論理的なまとまりごとに**わかりやすく解説する。
このスキルは理解の支援に徹し、評価や指摘は行わない（「良い/悪い」を判定するのはレビューの仕事）。

## Step 1: 解説対象の差分を特定する

`/explain-diff <指示>`のように引数で指示が与えられた場合は、その指示に従って対象範囲を決定する（デフォルトの自動判定より優先する）。
指示がない場合は「デフォルト判定」に従う。

### 引数で指示された場合

自然言語の指示をgitコマンドに読み替える。よくある指示の対応例：

| 指示の例                        | 対応するgit操作                                                                |
|-----------------------------|--------------------------------------------------------------------------|
| 「現在のブランチで行われた変更」「このブランチの変更」 | `git diff $(git merge-base <デフォルトブランチ> HEAD)`（分岐後の全変更。未コミット・コミット済み問わず含む） |
| 「ステージ済みだけ」                  | `git diff --staged`                                                      |
| 「このコミット」「直近のコミット」           | `git show HEAD`（コミットが指定されていればそのコミット）                                     |
| 「mainとの差分」「mainから今まで」       | 「現在のブランチで行われた変更」と同様（`merge-base`起点）                                      |
| 特定のコミットハッシュ・PR番号・ファイルパスの指定  | その対象に絞って`git diff`／`git show`を組み立てる                                      |

指示が上記に当てはまらない曖昧な表現の場合は、最も自然な解釈で範囲を決め、解説冒頭で「〜と解釈して解説対象とした」と明記する。

### デフォルト判定（指示がない場合）

`git status`と`git branch --show-current`を確認し、以下の優先順位で自動決定する。

1. 作業ツリーに変更がある → `git diff HEAD`を対象にする
2. 作業ツリーはクリーンだが、デフォルトブランチ以外にいる → `git diff <デフォルトブランチ>...HEAD`を対象にする
3. 作業ツリーがクリーンでデフォルトブランチ上にいる → 直近コミット（`git show HEAD`）を対象にし、その旨を一言断る

### 共通の注意点

`git diff HEAD`や`git show`には未追跡（新規追加）ファイルの内容は含まれない。
`git status`で未追跡ファイルを検出したら、Readツールで内容を確認し解説の対象に含めること。

解説の冒頭で「解説対象: HEADからの未コミット変更（5ファイル）」のように対象範囲を明記する。
差分がゼロの場合は解説せず、その旨を報告して終了する。

## Step 2: 差分と周辺コードを読み込む

`git diff --stat`で全体像（ファイル数・行数）を把握してから、差分本体を読む。

diffのハンクだけを日本語に直訳した解説には価値がない。
**変更された関数の全体、呼び出し元、関連する型定義など周辺コードをReadツールで確認してから解説する。**
これによって「何が変わったか」だけでなく「なぜそう変える必要があったか」まで語れるようになる。

## Step 3: 変更を論理単位に整理する

「ファイルの場所」ではなく「何をしているか」で変更をグルーピングする。
解説の章立てはこの論理単位に沿わせ、ファイル順のダラダラした列挙にはしない。

- 新機能とそのテスト → 1つのまとまり（同じ意図で追加された）
- 無関係な2つの修正が同居 → 別々のまとまりとして扱う
- 基盤変更（設定・スキーマ）とそれを使う機能変更 → 依存関係を意識して順序立てる

## Step 4: 図解が必要かを判断する

図はコストがかかる（HTMLを作りブラウザを開く手間が発生する）ため、差分の性質に応じて要否を判断する。

| 図解HTMLを作る                 | ターミナル解説のみで十分        |
|---------------------------|---------------------|
| 処理フロー・制御フローが変わった          | typo・フォーマット修正       |
| 複数ファイルにまたがる依存関係の変更        | 1〜2ファイルの局所的な単純修正    |
| データ構造・スキーマ・設定構造の変更        | docsのみの変更           |
| コンポーネント間のやりとりが新たに増えた      | 依存パッケージのバージョンbumpのみ |
| Before/Afterの対比が理解を大きく助ける | 差分を読めば数分で理解できる規模    |

迷ったときの経験則: 「図がこの差分の理解時間を体感で半分にするか？」。
Noならターミナルのみで完結させる。
ユーザーが「図で」「視覚的に」と明示した場合は、差分の規模によらずHTML図解を作る。

## Step 5: 解説を構成する

ターミナル解説・HTML解説共通で、次の4部構成にする（HTML側はこれをそのままページ内容にし、ターミナル側は要約に圧縮する）。

1. **全体サマリー**（2〜3文）— この差分は何を達成するか、なぜその変更が必要と推測されるか
2. **変更マップ**— ファイル×役割の一覧（例: `auth/token.go` — リフレッシュトークン検証の追加）
3. **論理単位ごとの詳細**— 各まとまりについて「何が」「どう変わったか」「なぜそう設計したと読めるか」。重要な箇所は`file_path:line`で引用する
4. **影響範囲・注意点**— 破壊的変更、動作が変わる境界条件、注目すべきポイント

## Step 6: 図を作る（HTML出力時のみ）

| 変更の性質               | 図の種類                    |
|---------------------|-------------------------|
| 処理の流れ・分岐の変更         | フローチャート（Before/After並置） |
| コンポーネント間の呼び出し・通信の変更 | シーケンス図風の縦タイムライン         |
| データ構造・設定・スキーマの変更    | Before/After2カラム比較      |
| ファイル間依存の追加・削除       | 依存関係図（ボックス＋矢印）          |

`assets/template.html`をコピーして使う。
このテンプレートには図解用のCSSコンポーネント（フローボックス、Before/After比較、依存関係図、diffハイライト）が一式揃っている。
**Mermaid.jsなど外部ライブラリ・CDNは使わない**（Artifactの厳格なCSPで読み込みがブロックされ、オフラインでも壊れるため）。
すべてインラインCSS/SVGで完結させる。

図は多くても1ページ3つまでにする。図を乱発すると逆にわかりにくくなる。

## Step 7: 出力する

- **Artifactツールが使える場合**: `assets/template.html`をベースに書いたHTMLをArtifactとして公開する。ターミナルにはURLと3〜5行の要約を出す。
- **Artifactツールが使えない場合**: スクラッチパッドディレクトリ（なければ`$TMPDIR`）にHTMLを書き、`open <file>`で開く。同様にターミナルへ要約を出す。
- **図解が不要と判断した場合**: Step 5の構成をそのままMarkdownでターミナルに出力する。

HTMLを開いたかどうかに関わらず、ターミナルだけ読んでも結論がわかる状態を保つこと。

## 注意事項

- gitの状態を変更するコマンド（`add`・`commit`・`checkout`・`reset`など）は実行しない。このスキルは読み取り専用。
- 差分が非常に大きい場合（目安2000行超）は、全ハンクを逐一解説せず、変更マップと主要な論理単位に絞って解説する。
- 日本語文中では英単語・数値の前後にスペースを入れない（例:「Bobである」であって「Bob である」ではない）。
