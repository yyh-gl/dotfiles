## 目的

[「敵対的検証」](https://zenn.dev/loglass/articles/6aa18c80496ec6)を行う。成果物を作った本人とは別の者が「間違っているはず」という前提で反証し、判定と根拠を返す手法で、次の4要件で成り立つ。

1. **独立性**: 作成時の文脈から切り離された目で検証する
2. **反証の役割**: レビュー（良い点も挙げる評価）ではなく、懐疑役として反証する
3. **接地**: 事実の主張は記憶ではなく一次情報で確かめる
4. **判断できる出力**: 指摘に深刻度と根拠を付け、採否を人間が決められるようにする

既存の`/code-review`（正確性のバグ探し）・`/security-review`・`codex-review`（Claude+Codexの統合レビュー）とは別物。「〇〇を直した」「△△に対応した」というPR説明やコミットメッセージの主張そのものを反証の対象にする点、懐疑役が作成時の会話の文脈を一切持たない点が異なる。

懐疑役を複数並列で起動するため、通常のレビューの3〜10倍のトークンを使う。この重さが、明示的なコマンド入力でしか起動しない理由。

## Step 1: 対象を解決する

引数を次のとおり解釈する。

| 引数の形 | 対象 |
|---|---|
| 数字、または`https://github.com/.../pull/<n>`のURL | PR |
| `A..B`または`A...B` | コミット範囲 |
| 上記以外の文字列 | ブランチ名 |
| 引数なし | 現ブランチ（後述のデフォルトブランチとの差分） |

対象はコミット済みの差分のみ。未コミットの変更、設計書・プランなどのファイルはこのスキルの対象外（対象を広げたい場合はスキルを使わず直接依頼する）。

### PRの場合

```bash
gh repo view --json nameWithOwner -q .nameWithOwner
```

```bash
gh pr view <引数> --json number,url,title,body,baseRefName,baseRefOid,headRefOid
```

`gh`は1回の呼び出しに単体で書く（パイプ・`;`・`&&`・`$(...)`・リダイレクトでほかのコマンドとつながない。絞り込みは`--json`・`-q`で行う）。

`gh pr view`が返す`url`から読み取れるowner/repoが、1つ目のコマンドで得た現在のリポジトリと異なる場合は、**検証せず中断**し「そのリポジトリで実行してください」と伝える。対象の内容（コミット・ブランチ）を取得できないため。

一致していれば、`baseRefOid`を`BASE`、`headRefOid`を`HEAD`とする。

### ブランチ・コミット範囲の場合

- コミット範囲（`A..B`・`A...B`）はそのまま`BASE`・`HEAD`にする
- ブランチ名が指定された場合、`HEAD`はそのブランチの先端、`BASE`は次で求めるデフォルトブランチ
- 引数なしの場合、`HEAD`は現ブランチの先端、`BASE`は次で求めるデフォルトブランチ。**現ブランチに対応するPRがGitHub上にあっても参照しない**（ローカルの差分だけを見る）

デフォルトブランチの求め方:

```bash
git symbolic-ref --short refs/remotes/origin/HEAD
```

失敗する・値が空の場合は、`origin/main`→`origin/master`→`main`→`master`の順で、`git rev-parse --verify <候補>`が通る最初のものを使う。

**現ブランチがデフォルトブランチ自身のとき**（引数なし、またはブランチ名として明示的に指定したとき）は、比較対象がないので中断し「検証したいブランチ・PR番号・コミット範囲を指定してください」と伝える。

### コミットの用意と差分の確認

`BASE`・`HEAD`がローカルのコミットとして存在するかを確かめる。

```bash
git cat-file -e <BASE>
```

```bash
git cat-file -e <HEAD>
```

どちらかが失敗したら、**sandbox内の`git fetch`はSSHリモートに失敗するため試さず**、ユーザーに実行を依頼して待つ。

- PRの場合: `! git fetch origin pull/<n>/head <baseRefName>`
- ブランチの場合: `! git fetch origin <branch>:<branch>`（またはユーザーの普段の取得方法）

両方そろったら差分の有無を確認する。

```bash
git diff --stat <BASE>...<HEAD>
```

出力が空なら中断し「差分がありません」と伝える（マージ済みPRで`BASE`がマージ後のベースブランチ先端を指し`HEAD`を含んでしまっている場合もここに該当する。疑わしければ`git merge-base <BASE> <HEAD>`と`<HEAD>`を比べ、一致するなら`BASE`の取り方を見直す）。

未コミットの変更（`git status -s`）があれば、それはこのスキルの対象に含めていない旨をStep 4のレポートの冒頭に1行書く。

### 主張を集める

```bash
git log <BASE>..<HEAD> --format=%B
```

これに、PRの場合は`title`・`body`を加えたものが「作者の主張」になる。**メインセッションの会話の経緯（なぜこう実装したか等）は集めない・懐疑役にも渡さない。** 懐疑役を作成時の文脈から独立させるため。

## Step 2: 懐疑役を起動する

固定の3観点を、**1つのメッセージで3つの`Agent`呼び出し**として並列に起動する。`subagent_type: "general-purpose"`・`model: "opus"`を指定する。`fork`は使わない（`fork`は現在の会話を引き継ぐため、懐疑役に必要な独立性が壊れる）。

| 観点 | 何を疑うか |
|---|---|
| 主張の反証 | 作者の主張（PR説明・コミットメッセージ）どおりに動くか。「〇〇を直した」が実際には直っていない、「△△に対応した」が一部のケースでしか成り立たない、といった食い違いを探す |
| 壊れ方 | この差分が入る入力・状態・境界・並行実行で、何が壊れるか。空文字列・null・巨大な値・想定外の型、競合状態、既存データとの不整合などを試す |
| 運用・互換性 | この差分を適用・移行・ロールバックする過程、既存の利用者・依存先との互換性で何が起きるか。設定変更の反映漏れ、後方互換の破壊、依存関係の衝突などを試す |

差分がこの観点に関係ない場合（例: ドキュメントだけの変更に対する「壊れ方」）、懐疑役は**判定を「該当なし」として理由を1行書き、早期に終了してよい**。無理に指摘を作らない。

### プロンプトの雛形

3体共通の部分:

```
あなたは独立した懐疑的レビュアーです。レビュー（良い点の指摘を含む評価）ではなく、反証を行います。
作成者の意図や経緯は一切考慮しません。以下の「作者の主張」は、信じるのではなく反証する対象として扱ってください。

## 対象
BASE: <BASEのSHA>
HEAD: <HEADのSHA>

差分: git diff <BASE>...<HEAD>
個別ファイルの中身: git show HEAD:<path>（変更後）、git show BASE:<path>（変更前）
履歴: git log、git blame
これ以外の方法でコードを変更・実行してはいけません。作業ツリーのファイルを書き換えたり、
git checkout・git switch・git worktree・gh pr checkoutでチェックアウトしたりしないでください。
コマンドやテストの実行もしないでください（接地は読解と一次情報の確認までで、実行検証はしません）。

## 作者の主張
<git log --format=%Bの出力。PRならtitle・bodyも>

## あなたの観点
<上の表から1観点ぶんの説明文>

## ルール
- レビューではなく反証する。良い点は書かない
- 指摘には必ず具体的な失敗シナリオ（どの入力・状態で、どう壊れるか）を付ける。付けられない指摘は出さない
- 確信の持てない推測は出さない
- 事実の確認は、コードの読解・grep・git log・git blameと、ライブラリ・ツールの挙動に関する公式ドキュメント・
  ソースの確認（WebFetch・WebSearch）まで。確かめられない事実は「未検証」と明記する
- この観点が今回の差分に当てはまらないと判断したら、判定を「該当なし」、理由を1行書いて終了してよい

## 出力形式
### 判定
GO／条件付きGO／NO-GO／該当なしのいずれかと、理由を1行

### 指摘（深刻度順）
各指摘につき:
- 深刻度: 高（主張が成り立たない、またはマージすると壊れる）／中（マージ前に修正が必要）／低（特定の条件でだけ問題になる）
- 失敗シナリオ: どの入力・状態で、何が起きるか
- 根拠: `HEAD:<path>:<line>`または`BASE:<path>:<line>`（コードの場合。変更前の行を指すときはBASE側を使う）、外部の事実なら出典URL
- 確度: 高／中／低

### 壊せなかった点
反証を試みたが崩せなかった点を1〜2行。なければ「なし」
```

3体すべての完了通知を待ってから次に進む。

## Step 3: 統合する

懐疑役の指摘の**妥当性は判断しない**（実装した本人が判断すると自分に甘くなるうえ、採否は人間が決めるべきもの）。行うのは次の機械的な確認だけ。

1. **重複のまとめ**: 同じ原因を指摘しているものを1つにまとめ、出典（どの観点の懐疑役か）をすべて併記する
2. **根拠の実在確認**: コードを根拠にした指摘について、`<側>:<path>:<line>`の`<側>`（`HEAD`または`BASE`）に応じて`git show HEAD:<path>`または`git show BASE:<path>`を実行し、該当行が実在するかを確かめる。確かめられない場合は指摘を**捨てずに**「根拠の行を確認できず」と注記する

## Step 4: レポートを出す

会話に次の順で書く。ファイルへの保存やPRへの投稿はしない。全体の判定（マージ可否の一言まとめ）は出さない。採否は人間が決めるため。

```markdown
## 敵対的検証: <対象の説明>（<BASE>...<HEAD>）

（未コミットの変更があれば、ここに「※未コミットの変更は対象に含めていません」の1行）

### 懐疑役の判定
- 主張の反証: <判定> — <理由>
- 壊れ方: <判定> — <理由>
- 運用・互換性: <判定> — <理由>

### 指摘（深刻度順）
#### [<深刻度>] <指摘の要約>
- 失敗シナリオ: <...>
- 根拠: <...>（確認できず、の場合はここに注記）
- 確度: <...> ／ 出典: <観点名、複数あれば列挙>

（以下、指摘の数だけ繰り返し）

### 壊せなかった点
- <観点名>: <内容>
（なければ「特になし」）
```

## 注意事項

- 作業ツリーには一切触れない。Step 1〜3のどの段階でも`git checkout`・`git switch`・`git worktree`・`gh pr checkout`・ファイルの書き込みを行わない
- Codexは懐疑役に加えない。別モデルの視点が欲しい場合は既存の`/codex-review`を別途使う（懐疑役がすべてopusのため、盲点を共有しうる点は既知の限界として受け入れている）
- 対象が大きすぎて懐疑役が読み切れない場合は、最も変更が集中しているファイル・ディレクトリに絞ってよいが、その旨を判定の理由に明記する
