# プラン文書テンプレート

以下のテンプレートに沿ってプラン文書を作成する。項目名は日本語のまま使い、
プロジェクトの言語慣習が英語の場合は英語に訳してよい。

```markdown
# <機能名> 実装プラン

- 仕様書: <仕様書ファイルへのパス or 出典>
- 作成日: <YYYY-MM-DD>

## 確定仕様

仕様書に書かれていなかった/曖昧だった点について、Q&Aで確定した事項を記録する。
「質問→決定→理由」の形で書くと、後から読んだときに判断の背景まで追える。

| # | 論点 | 決定 | 理由・補足 |
|---|------|------|-----------|
| 1 | <確認した論点> | <ユーザーの決定> | <なぜそう決めたか> |

## 委任ポリシー

フェーズ2（自律ループ）中に新たな不明点が出たときの事前契約。

| 区分 | 内容 |
|------|------|
| 暫定判断してよい範囲 | <例: 命名・ファイル配置・エラーメッセージの文言など、後から差し替えても手戻りが小さい実装詳細> |
| 必ず停止する条件 | <例: 外部インターフェースの変更、データの破壊的操作、確定仕様と矛盾する挙動が必要になった場合> |

## Quality Gate

各ブロック完了時に全項目クリアが必須。実際に実行するコマンドを明記する。

| 項目 | コマンド |
|------|---------|
| 全テストパス | `<例: npm test>` |
| lint/format | `<例: npm run lint>` |
| 型チェック/build | `<例: npm run typecheck>` |

- **リトライ上限**: <例: 3回。Gateが赤のまま同じブロックで何度修正を試みるか>

## 論理ブロック

依存関係順。各ブロックは単独でテスト・コミット可能な単位。
各ブロックに「自律実行可 / 人間の目が必要」のタグと、状態（未着手/実行中/完了/停止中）を持たせる。

### Block 1: <ブロック名> — [自律実行可 / 人間の目が必要] — 状態: 未着手

- **内容**: <このブロックで実装する振る舞い>
- **対象範囲**: <触るファイル・モジュールの見込み>
- **完了条件**: <このブロック固有の完了条件（Quality Gateに加えて）>

### Block 2: <ブロック名> — [自律実行可 / 人間の目が必要] — 状態: 未着手

...

## 現在位置

再開用ポインタ。新しいセッションはここだけ見れば続きから動ける。

- **現在のブロック**: <実行中/次に着手するブロック名>
- **最後に完了した作業**: <直近でコミット済みの作業内容>
- **停止中の場合の理由**: <委任ポリシー範囲外の疑問／リトライ上限到達など。該当なしなら「なし」>

## 暫定判断ログ

フェーズ2の自律ループ中に、委任ポリシーの範囲内で下した暫定判断の記録。

| # | いつ | どのブロック | 何を | なぜ |
|---|------|-------------|------|------|
| 1 | <日時> | <ブロック名> | <判断内容> | <委任ポリシーのどの範囲に基づくか> |

## 要求トレーサビリティ

Step 7の仕様突合レビューで埋める。仕様書の要求リストと実装・テストの対応表。

| # | 仕様書の要求 | 実装箇所 | テスト | 状態 |
|---|-------------|---------|--------|------|
| 1 | <要求> | <file:line> | <テスト名> | ✅ / ⬜ |
```

## 運用ルール

- ブロック完了ごとに状態（未着手/実行中/完了/停止中）と現在位置を更新する
- 実装中に確定した仕様は「確定仕様」の表に追記する
- 委任ポリシーの範囲内で下した暫定判断は、都度「暫定判断ログ」に追記する
- ブロックの追加・分割・削除をしたら、その旨と理由を残す（履歴が消えないように取り消し線などで）
- ブロックが停止中になったら、「現在位置」の停止理由を必ず埋めてから止まる
