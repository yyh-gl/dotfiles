## 目的

[「敵対的検証」](https://zenn.dev/loglass/articles/6aa18c80496ec6)を行う。成果物を作った本人とは別の者が「間違っているはず」という前提で反証し、判定と根拠を返す手法で、次の4要件で成り立つ。

1. **独立性**: 作成時の文脈から切り離された目で検証する
2. **反証の役割**: レビュー（良い点も挙げる評価）ではなく、懐疑役として反証する
3. **接地**: 事実の主張は記憶ではなく一次情報で確かめる
4. **判断できる出力**: 指摘に深刻度と根拠を付け、採否を人間が決められるようにする

既存の`/code-review`（正確性のバグ探し）・`/security-review`・`codex-review`（Claude+Codexの統合レビュー）とは別物。「〇〇を直した」「△△に対応した」というPR説明やコミットメッセージの主張そのものを反証の対象にする点、懐疑役が作成時の会話の文脈を一切持たない点が異なる。

懐疑役を複数並列で起動するため、通常のレビューの3〜10倍のトークンを使う。この重さが、明示的なコマンド入力でしか起動しない理由。

この変更（HTML出力・PRコメント案）の範囲は`/adversarial-verification`固有。dev-teamスキルのフロー（`~/.claude/agents/lead.md`・`~/.claude/skills/dev-team/SKILL.md`）は変更しない。

## Step 1: 対象を解決する

引数を次のとおり解釈する。

| 引数の形 | 対象 |
|---|---|
| 数字、または`https://github.com/.../pull/<n>`のURL | PR |
| `A..B`または`A...B` | コミット範囲 |
| 上記以外の文字列 | ブランチ名 |
| 引数なし | 現ブランチ（後述のデフォルトブランチとの差分） |

対象はコミット済みの差分のみ。未コミットの変更、設計書・プランなどのファイルはこのスキルの対象外（対象を広げたい場合はスキルを使わず直接依頼する）。

### PRの場合

```bash
gh repo view --json nameWithOwner -q .nameWithOwner
```

```bash
gh pr view <引数> --json number,url,title,body,baseRefName,baseRefOid,headRefOid
```

`gh`は1回の呼び出しに単体で書く（パイプ・`;`・`&&`・`$(...)`・リダイレクトでほかのコマンドとつながない。絞り込みは`--json`・`-q`で行う）。

`gh pr view`が返す`url`から読み取れるowner/repoが、1つ目のコマンドで得た現在のリポジトリと異なる場合は、**検証せず中断**し「そのリポジトリで実行してください」と伝える。対象の内容（コミット・ブランチ）を取得できないため。

一致していれば、`baseRefOid`を`BASE`、`headRefOid`を`HEAD`とする。

### ブランチ・コミット範囲の場合

- コミット範囲（`A..B`・`A...B`）はそのまま`BASE`・`HEAD`にする
- ブランチ名が指定された場合、`HEAD`はそのブランチの先端、`BASE`は次で求めるデフォルトブランチ
- 引数なしの場合、`HEAD`は現ブランチの先端、`BASE`は次で求めるデフォルトブランチ。**現ブランチに対応するPRがGitHub上にあっても参照しない**（ローカルの差分だけを見る）

デフォルトブランチの求め方:

```bash
git symbolic-ref --short refs/remotes/origin/HEAD
```

失敗する・値が空の場合は、`origin/main`→`origin/master`→`main`→`master`の順で、`git rev-parse --verify <候補>`が通る最初のものを使う。

**現ブランチがデフォルトブランチ自身のとき**（引数なし、またはブランチ名として明示的に指定したとき）は、比較対象がないので中断し「検証したいブランチ・PR番号・コミット範囲を指定してください」と伝える。

### コミットの用意と差分の確認

`BASE`・`HEAD`がローカルのコミットとして存在するかを確かめる。

```bash
git cat-file -e <BASE>
```

```bash
git cat-file -e <HEAD>
```

どちらかが失敗したら、**sandbox内の`git fetch`はSSHリモートに失敗するため試さず**、ユーザーに実行を依頼して待つ。

- PRの場合: `! git fetch origin pull/<n>/head <baseRefName>`
- ブランチの場合: `! git fetch origin <branch>:<branch>`（またはユーザーの普段の取得方法）

両方そろったら差分の有無を確認する。

```bash
git diff --stat <BASE>...<HEAD>
```

出力が空なら中断し「差分がありません」と伝える（マージ済みPRで`BASE`がマージ後のベースブランチ先端を指し`HEAD`を含んでしまっている場合もここに該当する。疑わしければ`git merge-base <BASE> <HEAD>`と`<HEAD>`を比べ、一致するなら`BASE`の取り方を見直す）。

未コミットの変更（`git status -s`）があれば、それはこのスキルの対象に含めていない旨を、Step 5で生成するHTMLのヘッダーとターミナル要約に書く。

### 主張を集める

```bash
git log <BASE>..<HEAD> --format=%B
```

これに、PRの場合は`title`・`body`を加えたものが「作者の主張」になる。**メインセッションの会話の経緯（なぜこう実装したか等）は集めない・懐疑役にも渡さない。** 懐疑役を作成時の文脈から独立させるため。

## Step 2〜4: 懐疑役の起動・統合・レポート

共通手順は`references/skeptics.md`に切り出した（dev-teamスキルからも参照されるため）。このスキルでは次のとおり当てはめる。

- **Step 2（懐疑役の起動）**: `references/skeptics.md`の「懐疑役を起動する」に従う。「作者の主張」として渡すのは、Step 1で集めた主張（`git log <BASE>..<HEAD> --format=%B`のコミットメッセージ。PRの場合はタイトル・本文も）
- **Step 3（統合）**: `references/skeptics.md`の「統合する」に従う
- **Step 4（レポートの統合）**: `references/skeptics.md`の「レポートを出す」の構成（判定→指摘→壊せなかった点）で統合結果をまとめる。全文は会話に出さず、Step 5でHTMLに埋め込む。ターミナルにはStep 5で作る要約だけを出す

## Step 5: HTML出力とPRコメント案

Step 4でまとめた統合結果を、`assets/template.html`をベースにしたHTMLファイルとして出力する。あわせて、対象がPRのときだけPRコメント案を機械的に作る。

### コード抜粋を切り出す

Step 3の根拠の実在確認で得た`git show <側>:<path>`の結果から、各指摘の根拠行の前後±3行をメインセッションが機械的に切り出す。「根拠の行を確認できず」の指摘、または根拠が出典URLのみの指摘にはコード抜粋を付けない。

### PRコメント案を作る（対象がPRのときだけ）

対象がブランチ・コミット範囲の場合はこの節を行わず、HTML解説のみ出力する。

対象がPR（Step 1で引数が数字またはPR URLと判定したケース）のときは、**全指摘**（深刻度・確度を問わず、「根拠の行を確認できず」の注記付きの指摘も含む）にPRコメント案を機械的に作る。どれを実際に使うかはユーザーが選ぶため、メインセッションは指摘を選別しない。

1つの指摘に根拠が複数あるときは、差分内の根拠を優先し、差分内に複数あればそのうち先頭に書かれたものを使う。その根拠に対して次の位置決定を行う。

**コメントを置く位置**（次の4段を上から順に試し、最初に当たったものを使う）:

1. 根拠のファイルが`git diff --name-only <BASE>...<HEAD>`に含まれ、かつHEAD側の行が差分のハンク内 → その行（RIGHT側）
2. 根拠のファイルが差分に含まれ、かつBASE側の削除行が差分のハンク内 → その行（LEFT側）
3. 根拠のファイルは差分に含まれるが、行がハンク外 → ファイル単位のコメント
4. 根拠のファイルが差分に含まれない、または根拠が出典URLのみ → PR全体へのコメント

ハンク内外の判定は`git diff -U0 <BASE>...<HEAD> -- <path>`のハンクヘッダーと根拠の行番号を照合する。ハンクヘッダーは`@@ -a[,b] +c[,d] @@`の形式で、件数（`b`・`d`）を省略した場合は1、件数が0ならその側に行はないものとして扱う。根拠がHEAD側の行Nなら`c ≤ N < c+d`を満たすハンクを、BASE側の行Nなら`a ≤ N < a+b`を満たすハンクを探す。

**コメントの文面**: 確度「高」の指摘は言い切り（「〜になります」）、確度「中」「低」の指摘は疑問形（「〜になりませんか？」）で書く。内容は「どの条件で何が起きるか」を1〜2文にする。懐疑役は修正案を出さない原則のため、修正の方向は含めない。表記は`~/.claude/skills/writing-voice/references/grammar-checklist.md`の日本語表記ルール（英単語・数値前後のスペーシング等）だけを機械的に適用する。`writing-voice`スキルのフル起動（Step 0〜4、過去サンプルの`gh`収集）は行わない。

### HTMLに書き出す

HTMLへ埋め込むすべての可変テキスト（コード抜粋、懐疑役の文章（失敗シナリオ・壊れる経路・判定の理由・壊せなかった点）、PR説明文やコミットメッセージの引用、PRコメント案の文面、ファイルパス、ブランチ名など）は、`<` `>` `&` `"`をすべてエスケープしてから埋め込む。エスケープは`&`を最初に置換すること（後に回すと`&lt;`が`&amp;lt;`になる）。検証対象は他人（または過去の自分）のコード・PR本文であり、`<script>`のような文字列を含みうる。ローカルHTMLファイルにはArtifactのCSPがなく、エスケープを怠ると開いた瞬間にスクリプトが実行されるおそれがある。

`assets/template.html`をコピーし、ヘッダー（対象の説明・BASE/HEADのSHA・未コミット変更や対象を絞った旨の注記があれば追記）・懐疑役の判定3件・指摘一覧（深刻度順）・壊せなかった点を埋める。懐疑役が対象を絞った場合（`references/skeptics.md`「対象が大きすぎる場合」）も、HTML生成・PRコメント案の生成は出た指摘の範囲でそのまま行い、絞った旨は判定の理由としてそのままHTMLに表示する。

書き出すファイル名は次の規則にする: `adversarial-verification-<対象の短い識別子>-<BASEの短SHA>-<HEADの短SHA>.html`。

- 対象の短い識別子: PR番号なら`pr<n>`、ブランチ・コミット範囲ならrefの文字列から`[A-Za-z0-9._-]`以外の文字をすべて`-`に置換したもの
- 短SHAは、手元で確認済みのフルSHAの先頭7文字（`git rev-parse --short`などコマンドを新たに実行しない）

`Write`ツールでスクラッチパッドディレクトリに書く（`claude/CLAUDE.md`によりリダイレクトでの書き込みは使わない）。

### ターミナルへの要約

ターミナルには要約だけ出す:

- 懐疑役3体の判定（観点・判定）
- 指摘の件数と最大深刻度
- HTMLファイルの絶対パスと、`! open <絶対パス>`での開き方の案内（sandbox内から`open`は使えないため）
- 対象がPRのときのみ、PRコメント案の件数

詳細（コード抜粋・壊れる経路・コメント案全文）はHTML側に書く。HTMLを開かなくても判定・件数・最大深刻度が分かる状態を保つ。

PRへの実際の投稿は行わない。あくまで提案に留める。

## 注意事項

- 作業ツリーには一切触れない（書き込みを含む）。Step 1〜5のどの段階でも`git checkout`・`git switch`・`git worktree`・`gh pr checkout`・作業ツリーへのファイルの書き込みを行わない。ただしStep 5でスクラッチパッドディレクトリ（作業ツリー外）にHTMLファイルを1つ書くことだけは例外
- Codexは懐疑役に加えない。別モデルの視点が欲しい場合は既存の`/codex-review`を別途使う（懐疑役がすべてopusのため、盲点を共有しうる点は既知の限界として受け入れている）
